## 1. 目标与当前位置

总目标不变：Drone 是通用 Pi 桌面宿主，科研功能全部来自可安装、可停用的标准 Pi 包；卸载科研包后 Drone 仍能构建、启动和聊天；最终是一个好用、功能贴切的科研智能体。执行清单是 [P0–P7 计划](pluginization/native-plugin-implementation-plan.md)（含 2026-10-29 用户确认的执行方式修订）。

P4 = 把任务插件（`@gyoungwe/pi-core` 的任务状态机）从“启动期进程内 taskHost”迁到受管插件运行时，并删除宿主里的启动期 taskHost/coreHost 装配。分四步：

| 步骤 | 内容 | 状态 |
| --- | --- | --- |
| 1 | 宿主签发的任务授权（一次宿主对话框） | ✅ main（Drone #241） |
| 2 | 宿主配套能力：自动续作、状态卡、按当前读权限读工作区；只读 hook 可用的簿记/提问 | ✅ main（Drone #242，`838362de`） |

| 4 | 补齐受管路径缺口 → 安装包真实验收 → 切换清单 → 删除启动期 taskHost/coreHost 与旧桥 | ⏳ 未开始，下一步从这里做（见 §5.2） |

### 4.1 收尾时修复的受管路径问题（drone-plugins #3，Drone #244）

第一次锁定 #2 时，Drone `plugin-provider-sdk.test.mjs` 的 5 个受管 TaskSession 用例失败（Linux 同样复现，不是 macOS 时序问题）。三个问题都只在受管路径出现，原生 Pi 不受影响：

1. **运行中发状态卡**：`turn_end`/`agent_end` 仍在 SDK 运行内，宿主拒绝 `session.notify`（`requires an idle session`），adapter 把拒绝当存储失败，TaskSession 被隔离成 needs-reopen。现在受管 ports 声明 `statusAfterRun`，运行中只暂存，到 `agent_settled` 再发；宿主 `NATIVE_EVENTS` 新增 `agent_settled`。
2. **发卡没有等待**：broker 只在 hook/工具/命令执行期间借出能力，未 `await` 的发卡到达时调用已结束（`caller completed`），用户发一句“任务状态”也会触发。现在所有 `send()` 都在调用内等待。
3. **隔离后读状态抛错**：`journal.refresh` 对已隔离的会话也跑 storage turn，于是 status 抛错，而不是返回最后确认的状态。已恢复 #2 之前的受管语义。

插件单元测试的假宿主原来不模拟这两条宿主规则，所以插件 CI 没发现；现在模拟了。规则记在 [PITFALLS](PITFALLS.md#受管插件的状态卡要等运行结束在调用内等待)。

### 5.2 补齐受管路径的已知缺口（切换前必须解决或经用户明确取舍）
1. **PDF DOI/标题身份核对**（2026-11-07 已解决）：受管进程不能加 `--allow-worker`（worker 可借 `execArgv: []` 脱离 `--permission`，见 PITFALLS），所以由宿主提供 `document.pdfText`（Drone #263），每次新起一个受限一次性进程解析；pi-core 受管 ports 把它传给 `inspectTaskBytes` 的 `readPdfText`（drone-plugins #14，锁定 6d1cfb4），原生路径仍用 worker。真实证据：`packages/backend/test/managed-pdf-identity-sdk.test.mjs`（真实 SDK 会话、受限进程、已安装 pi-core，任务面板交 PDF 后得到 `metadata-matched`，别的论文被拒）；换回旧 pi-core 或去掉宿主能力都会让它失败。
2. **Vault（知识库绑定）文件验收**（2026-11-07 已解决）：pi-knowledge 新提供 `knowledge.binding` 服务（只返回 `vaultId`、`revision`、Vault 真实路径，不返回内容，由它自己读 `binding.json`），pi-core 受管 ports 经 `requires.knowledge` 调用它取得绑定，按原生路径的规则核对任务绑定未变、文件仍在 Vault 内，文件本身由宿主 `workspace.readFile` 按会话当前读权限读取（drone-plugins #15，锁定 c4052a6）。宿主不解析 Vault 数据。切换时 pi-core 清单需加 `requires: { knowledge: { service: "knowledge.binding", version: 1 } }`，现有 SDK 夹具已提前加上。真实证据：`packages/backend/test/managed-vault-acceptance-sdk.test.mjs`（真实 SDK 会话、受限进程、已安装 pi-core 与真实 pi-knowledge：Vault 笔记让里程碑完成；改绑 Vault 后旧绑定下的笔记不再被接受）；换回旧锁或去掉 pi-knowledge 的 `provides` 都会让它失败。
3. **其他插件注册的验收器**（例如 Zotero 文献核对 `zotero-literature`，示例任务依赖它）：进程内版本靠 `pi.events`；受管版本需要设计里的跨插件“验收器角色”，在提供者 owner 内执行，复核来源与会话。设计见 [跨插件验收器角色](superpowers/specs/2026-11-05-task-acceptance-role-design.md)：用户已选 Zotero 提前到 P4（方案 A）与通用网络能力（N1）；`consumes` 前缀枚举、`rebind` 由宿主弹框两点也已选定（2026-11-05）。正向 `zotero_item` 验收器已完成（Drone #250、drone-plugins #7，`packages/backend/test/managed-acceptance-role-sdk.test.mjs`）；剩下的是计划内工作、无待定决策：宿主凭据引用（凭据 PR 2–4）、授权内一次性写入令牌、重锁研究包后用真实研究包验收，以及切换时删除 `zotero-literature.mjs`。进度见设计文档“Zotero 迁移进度”。
4. **决策记录、宿主能力检查点、上下文淘汰事件**（2026-11-08 已解决）：宿主新增只读的 `session.capabilities`（本会话分支最新的 `drone-capability-checkpoint-v1`）和 `session.decision.record`（写入，`approval: own`，不弹框；记录编号由宿主加插件 ID 前缀，项目与时间由宿主填写），并把 `drone:context-evicted` 作为插件事件转发（只发给本会话的插件，载荷重建为 `{sessionId, toolCallIds}`）（Drone #266）。pi-core 受管 ports 用它们取能力检查点、在任务授权与改绑确认后记决策、在淘汰后让证据窗口可恢复（drone-plugins #16，锁定 0a7db49）。真实证据：`packages/backend/test/managed-host-events-acceptance-sdk.test.mjs`（真实 SDK 会话、受限进程、已安装 pi-core：任务记下检查点里的能力；面板授权后宿主收到决策且没有多余弹框；会话报告淘汰后 `task_evidence_restore` 取回被淘汰的那一行）；去掉 pi-core 三处接线中的任何一处或不发淘汰事件，都会让对应用例失败。
5. **`sendUserMessage("继续")` 与续作提示**（2026-11-05 用真实 SDK 复现，用例 `packages/backend/test/managed-task-continue-sdk.test.mjs`）：原描述的“无授权、无里程碑”任务现在造不出来（`task_plan` 必须带里程碑，没有计划时 `task_wait` 直接报错），空闲时的“请发送继续”卡片也能送达。实际查出三个问题：① 任务面板选“仅核对已有产物”时 `progress-action.mjs` 的 `send()` 未 await，调用结束后发卡被拒、会话被隔离成 needs-reopen（并发 6/18 次）；② 自动接续用完 16 次后 `agent_end` 应询问用户，但 `progressTask` 先检查空闲而运行仍在进行，错误被 `catch {}` 吞掉，询问框不弹；③ 受管适配器把宿主的续作预算（授权框里的 3 次）用在例行接续上，原生路径的接续上限是 16 次，6 阶段任务做到第 4 次接续就停下。①② 已修复（询问挪到 `agent_settled`）；③ 用户选定 19 次（16 次例行接续 + 3 次恢复），pi-core 请求 `maxAutoResumes: 19`（drone-plugins #6），宿主 schema 上限同为 19（已解决）。真实 SDK 已确认：`session.select` 在 `agent_end` 与 `agent_settled` 都可用，`session.notify` 只在 `agent_settled` 可用。

## 7. 环境与流程上的坑

- **GitHub**：本环境不能用 GraphQL（`gh pr create` 会 403），用 REST：`gh api repos/Gyoungwe/<repo>/pulls -f base=main -f head=<branch> -f title=... -F body=@file`；合并 `gh api -X PUT repos/.../pulls/<n>/merge -f merge_method=merge`。
- **root 运行的测试**：`execution-runner.test.ts` 与 `state-reservations.test.ts` 各有一项依赖 chmod 故障注入，root 下必失败，CI（非 root）通过。
- **桌面构建 OOM**：容器里 `npm run build` 可能堆内存不足，用 `NODE_OPTIONS=--max-old-space-size=6144`。
- **Windows CI**：三个 Windows job 在 main 上就失败（`continue-on-error`），原因记录在 `docs/PITFALLS.md`；判断 PR 时只看 macOS/Linux。新测试若用 `os.homedir()`，同时 stub `HOME` 与 `USERPROFILE`。
- **本地仓库（用户 Mac）**：主仓库 Drone `~/Documents/ChatGPT/Drone`、插件 `~/Documents/ChatGPT/drone-plugins`，当前检出的是旧的 `codex/scientific-agent-upgrade` 分支，很久没 fetch，看状态前先 `git fetch`。第 3 步收尾用的是独立 clone `~/Claude/Projects/小菜蛾基因筛选/Drone-dev/{Drone,drone-plugins}`。旧整合工作树 `/tmp/drone-native-domain-owner-integration` 已被系统清理。
- **Cowork VM**：没有 GitHub 凭据，git 访问 GitHub 也不稳定；推送和合并由用户在 Mac 上用 `gh` 执行。中文路径会被脚本里的 `new URL(...).pathname` 转码，门禁要复制到 ASCII 路径（如 `/tmp`）跑；`permission-extension.test.ts` 需要 `TMPDIR` 不在 `$HOME` 下；VM 没有 linux-arm64 的锁定插件运行时，需按官方 SHASUMS 校验后手工暂存（目录已被 gitignore）。
- **受管插件机制要点**：调用结束后 broker 不再借出能力（定时器里或未 `await` 的调用会失败）；SDK 运行期间不能 `session.notify`，状态卡等 `agent_settled`；创建会话时没有 live caller；`session_shutdown` 不经过 broker；只读调用只能用 `readCallable` 的写能力。
