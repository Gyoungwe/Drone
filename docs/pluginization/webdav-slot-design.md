# WebDAV credential slot and plugin cutover design

Design for T33, inspected at Drone `777c5677a6be4c965779e70f3fd8a915e8244189` on 2026-11-16.
This is a source-based implementation proposal, not runtime acceptance. Paths below are relative to Drone unless prefixed `drone-plugins:`. Proposed filenames and contract additions are identified explicitly.

## Fixed decisions

- The host owns the `@gyoungwe/pi-knowledge` / `webdav` credential slot, using the existing `PluginCredentialStore` and its 0600 `agentDir/plugin-credentials.json`. The plugin names the slot; it cannot read the file or password.
- Cutover does not import, inspect, clear, rewrite, rename or delete `knowledge-webdav.json`. Without an environment override or a newly entered slot password, WebDAV is **Not configured**. There is no migration/adoption ticket and no second secret store.
- A nonempty host `DRONE_WEBDAV_PASSWORD` takes precedence over the slot. Only host code reads it. Supplying the credential to the plugin means servicing its authenticated network request, never sending the password to a worker, model or UI response.
- Remote and local mutations use the existing `workspace-write` authorization boundary plus declared network access. Do not introduce a WebDAV/cloud approval category, background synchronization or deletion propagation. B8 remains deferred.

These decisions supersede the credential/adoption alternatives in `docs/pluginization/inventory-host-knowledge.md:278` and the resolved parts of Q2 at `docs/pluginization/inventory-host-knowledge.md:303`.

| `authentication` | Proposed additive mode `http-basic-digest`; absent means today's literal-header behavior. This is a contract addition, not a currently supported field. |

Keep the package's current Pi/Desktop host declarations. The new managed WebDAV flow uses host capabilities; without them, report unavailable and make no request. Native Pi must not grow an independent password-file or environment-reading fallback.

The plugin owns WebDAV endpoint/username/folder configuration and existing defaults, subject to Q1. The host owns validation of every actual destination against both slot and manifest hosts. Generic HTTP takes an additive `httpAuth: { username: string }` request argument for a slot declaring `authentication: "http-basic-digest"`; username is a non-secret connection parameter, never a replacement for the slot password. Validate it at the host boundary using the existing username rules. Require this argument for that mode; never send a raw password as Authorization.

An older host rejects the new request argument before network IO (`additionalProperties:false` in `packages/backend/src/plugins/network-capabilities.ts:31`). The plugin must check the returned slot authentication metadata first and report unavailable on an older host. Update the manifest parser, source identity and slot-definition hash to include the new mode; retain existing literal-header slot keys unchanged. Do not adopt any old WebDAV record while doing so.

## Target call path and transport split

1. User enters a new password in the existing host credential settings row. Existing save/clear methods write/read back the generic slot; successful results contain no secret. Saving never tests the network and never modifies the host environment.
2. Managed knowledge UI uses `usePluginRuntime()` and caller-scoped operations proposed as `cloud.status`, `cloud.probe`, `cloud.initialize`, `cloud.read`, `cloud.write` and `cloud.sync`. The runtime asks `credentials.status` and sends `credential: "webdav"` on network calls. No plugin-side filesystem, `fetch`, `process.env`, password setter or credential reader is added.
3. A host-owned resolver, injected into the existing source capability assembly, chooses the nonempty `DRONE_WEBDAV_PASSWORD` for this exact package/slot, otherwise `PluginCredentialStore.get`. It reads the environment on each status/request, without copying it into JSON, plugin process environment or bootstrap payload. A wrong environment password remains an authentication failure; never retry with the saved password.
4. `network.read` gains PROPFIND; `network.write` gains MKCOL. GET/HEAD/PROPFIND are reads; MKCOL/PUT and local pull writes retain `workspace-write` approval and current grant/revocation checks. PROPFIND is Depth 0 only for this flow. Do not overload the existing POST-only `drone.networkReads` declaration. The current method sets lack these verbs (`packages/backend/src/plugins/network-capabilities.ts:11`).
5. The host's generic HTTP layer resolves the secret **after** destination validation and authorization. It owns Basic/Digest challenge parsing, hashing and nonce state, permits the existing MD5/MD5-SESS/auth combinations, prefers Digest and sends Basic only after a Basic challenge. One authentication challenge exchange is part of the authorized request, not a new write grant or a retry of an uncertain write. Scope challenge state to the source, origin and credential selection; clearing/replacing a slot or changing the override invalidates it.
6. Plugin WebDAV modules own collection URLs/XML, DAV multistatus interpretation, folder initialization, note selection/path rules, UTF-8, 64 KiB XML/1 MiB note limits, strong ETags, preview/binding fences and conflict decisions. The host retains its generic response ceiling, cancellation, no redirects, root confinement, atomic writes and CAS. Local mutations go through existing `files.*` ports with the selected writable Vault grant, never the old host knowledge facade.
7. Before reporting a mutation as verified, read back collection/note/hash or local file through the same authorized ports. A failed/mismatched readback leaves an explicit unverified/unknown result. Network loss after PUT is unknown and cannot trigger an automatic resend. No operation propagates a deletion or schedules a retry.

Keep credential-bearing HTTP below the broker; do not give the plugin a password to implement Digest. Conversely, do not leave XML parsing, cloud status policy, knowledge-note rules or sync orchestration in the host's generic HTTP capability. New host modules are proposed as `plugins/http-auth.ts` and `plugins/http-transport.ts`; the separate research writer consumes the generic transport through an injected credential callback when its old import is removed.

### Status and disclosure rules

Extend the generic credential status and settings projection additively with `source: "env" | "saved" | null`, `savedConfigured: boolean` and authentication mode. `configured` describes the effective credential; existing `fields`/`values` stay non-secret. Both projections must use the same resolver. Configuration presence is distinct from connection/authentication success.

| Inputs | Display and behavior |
| --- | --- |
| Legacy file only; no env/new slot | **Not configured**; `source:null`, `configured:false`, cloud mode disabled. Offer entry under pi-knowledge credentials; no probe on page open/startup. Legacy file existence/content has no effect. |
| New slot only | **Configured — saved on this computer**; connection remains unchecked until explicit probe. |
| Env only | **Using DRONE_WEBDAV_PASSWORD**; effective configured state true, saved state false. Clearing an absent slot does not clear the environment. |
| Env plus slot | **DRONE_WEBDAV_PASSWORD overrides the saved password**; save/clear affects only the slot. Clearing it leaves env active; unsetting env reveals the newly saved slot or Not configured. |
| Rejected storage/auth/network operation | Fixed safe error code/message; show failure, never configured/verified success based on an unsuccessful save or remote write. |

Recompute status after save/clear and before explicit network operations. Status/logs/errors/audit/IPC results never contain passwords, Authorization, cookies, challenge material or echoed request bodies. For authenticated HTTP, discard error bodies and return only the response headers needed by WebDAV (ETag, Last-Modified, Content-Type/Length); inspect 401 challenges inside the host. The current generic broker returns all response headers/bodies (`packages/backend/src/plugins/network-capabilities.ts:121`), so host filtering is required, not supplied by today's API. Logs/receipts must also exclude Vault and session content.

## Open questions and stop points

1. **Connection defaults and endpoint override:** The five decisions do not settle whether to retain today's endpoint/username/folder defaults or the arbitrary `DRONE_WEBDAV_ENDPOINT` override. Approve the exact manifest host[:port] list and the non-secret endpoint handoff if that override remains. A new origin requires an explicit declaration/trust change; do not silently broaden hosts, read environment in the plugin or add a new configuration UI. Stop W1/W2 connection-contract work until settled.
2. **Published API retirement:** Which concrete Plugin API/host release may remove the seven public cloud aliases and channels? Current 1.x compatibility rules forbid an unversioned removal. Stop W3 until the manager supplies the version and any required consumer transition policy; no fallback layer is selected here.
3. **XML dependency:** The inspected pi-knowledge package has no XML dependency, while the current host uses `@xmldom/xmldom` (`packages/backend/src/knowledge/webdav-transport.ts:3`). Approve reuse of that parser/version in the plugin, or identify an already approved parser before W1 implements DAV XML handling. Do not install/download or substitute a regex parser during this ticket.

There are no open decisions about migrating the password, deleting/clearing the old file, adding a secret store, environment-password precedence or a new approval category: all are fixed above. No index/source ownership changes are made by this design-only ticket; `docs/INDEX.md` remains untouched under T33's one-file boundary.
