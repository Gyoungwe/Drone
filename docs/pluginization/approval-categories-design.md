# Approval categories and reuse design

Date: 2026-11-16. Ticket: T32. Source baseline: `777c5677a6be4c965779e70f3fd8a915e8244189`.
Status: implementation proposal, not implemented or runtime-accepted. Policy choices in Open questions remain undecided and block their dependent tickets.

## Fixed decisions and scope

- Add `subprocess-install`, with the host prompt **“Install and start external program <name>”**, covering uv / zotero-mcp-server installation and bootstrap, plus MCP child start on enable/reload. Make the broker reusable by other plugins.
- Add `background-model-spend` for unattended maintenance/radar model calls and replay/multipath/eval model spend. It is off by default; enabling requires a user-set daily budget.
- WebDAV cloud read/write reuses `workspace-write` plus declared network access. Research state, analysis freeze/import, and source-traceable Inquiry automatic ledger writes reuse `application-state-write`. Capsule export requires a separate confirmation for every export. Drop Inquiry results arriving after revocation.
- Only the host creates, narrows, replaces or revokes authorizations. A plugin may request work or consent; its declarations, answers, saved JSON, provider payloads and task journals cannot issue or widen grants. Managed plugins never receive `--allow-worker` or direct child-process permission.
- This design does not implement domain migration, retire resources, change locks, delete data, or implement deferred B8 cloud collaboration. WebDAV here is the existing knowledge sync flow.

## Proposed additive contract

Keep categories distinct from effects (`read`/`write`), capability names, task allowances and raw executable names. The following is a proposed manifest fragment, not syntax supported by today's decoder:

```json
{
  "entrypoints": { "desktopRuntime": "./dist/desktop-runtime.mjs" },
  "permissions": {
    "filesystem": ["application-state-write", "workspace-write"],
    "network": ["configured-services", "astral.sh", "pypi.org", "files.pythonhosted.org"],
    "subprocess": ["subprocess-install"],
    "model": ["background-model-spend"],
    "externalWrites": true
  },
  "drone": {
    "subprocessInstall": {
      "uv": { "name": "uv", "plan": "./resources/uv.install.json" },
      "zotero-mcp-server": {
        "name": "zotero-mcp-server", "plan": "./resources/zotero-mcp.install.json"
      }
    }
  }
}
```

Use each category only in plugins that need it; this combined fragment is not a required permission bundle. WebDAV uses its separately declared exact host including port, not any installer hosts above. `configured-services` permits model selection, not arbitrary HTTP. Neither budgets nor enabled flags come from manifests.
Add public category, plan, request/result and denial types in a new `packages/plugin-api/src/approvals.ts`, re-exported by the existing root/runtime surfaces. `permissions.model` is optional and absence denies background spend. A declared install target requires `subprocess-install`, its packaged plan and a desktop runtime; no target is inferred from the legacy executable-name list.
Plan files are versioned declarative inputs: probes, install steps, artifacts/origins/integrity, destinations, and the start executable/argv. Validate them as untrusted manifest content; resolve packaged paths inside the verified package. The host freezes the resolved plan and hashes it, including platform, artifact identity, exact argv and writable locations, before asking. Target input cannot supply replacement commands, environment variables or paths. Exact installer versions/platform plans remain Q5.
Declarations must be included in installed content identity/source comparison and rejected when unsupported. Update plugin manifest checking/specification before declaring them in production packages. Existing grants do not gain new categories on upgrade.

## `subprocess-install`

Proposed capability `subprocess.installAndStart({target})` names one declared target. The host resolves its installed source/plan, displays the exact required prompt with the validated display name, and shows install locations, download origins, resolved commands, program version and start lifetime in detail. uv and zotero-mcp-server are separate named approvals unless the user explicitly approves a displayed combined plan (Q5).
Ask before the first probe that executes a program, before any installation/bootstrap side effect, and before a managed MCP child starts on enable/reload without a current matching grant. An installed binary, MCP `enabled: true`, a task grant, or previous installation success is not start authority. Checking file existence need not spawn. Denial must not enter the old direct installer or generic MCP reload path.

Host-only live record shape (not plugin request fields):

```ts
type SubprocessInstallGrant = {
  id: string; category: "subprocess-install";
  source: { pluginId: string; contentHash: string };
  applicationId: string; activationId: string; approvingOwnerId: number;
  target: string; planHash: string; executableIdentity: string;
  allowedSteps: readonly string[]; issuedAt: string; generation: number;
};
```

The host maintains accepted steps and child ownership beside the grant; the plugin receives only an opaque process handle and redacted installed/started status. Recheck the live generation, current source, executable/artifact identity and cancellation immediately before each step/start. A changed plan, version, destination or executable requires a new host decision, never an amendment from plugin JSON.
The host executes installer/probe/MCP children itself and owns stdin/stdout framing, cancellation, exit/drain and post-install/config readback. Keep the managed worker sandbox as demonstrated by `packages/backend/src/plugins/process-runtime.ts:283`; a host-owned external child does not imply `--allow-worker`, shell, network or spawn access for the plugin. Keep generic MCP policy as an additional gate, not an alternate unapproved launch route. Never forward raw environment credentials to the worker.
Revocation invalidates the generation first, rejects queued starts, cancels in-flight installation and stops/drains owned MCP children. Plugin disable/update/removal, source change and activation disposal invalidate live grants. Do not uninstall software or delete shared data on revoke. Cancellation after a side effect must report the actual partial state, verified by host readback.
Persist no executable live grant by default in this proposal: it is activation-local like existing root grants. If durable reuse is desired, Q4 must first settle its lifetime; any saved consent would be a host-only JsonStore record bound to source/plan, revalidated before issuance. Non-authorizing install/config receipts may persist via existing host JsonStore paths; do not store stdout, secrets or session text. This category has no daily model budget and cannot authorize model spend.
Missing declaration/target is unavailable; rejection of consent returns the existing capability failure form `Plugin capability denied: subprocess.installAndStart`. Revoked callers reject after cleanup and return no live handle. Current process transport carries error messages (`packages/backend/src/plugins/process-runtime.ts:629`); do not promise structured error codes without changing that protocol.

## `background-model-spend`

Use separate host capabilities `model.background.selection`, `model.background.generate` and `model.background.toolStep`. Their category is fixed by the host; no plugin boolean turns a request into foreground work. Bind every scheduled/replay/multipath/eval invocation to a host-created background caller and source/generation. Nested provider calls preserve that classification; task allowances and the generic task-grant exemption never satisfy it.
The host binds scheduled jobs and registered replay/multipath/eval entry operations to that purpose at dispatch. Existing `model.generate`/`model.toolStep` must inspect this host-only lineage too: choosing the old capability name cannot bypass the budget. The exact workflow-entry contract is part of Q3/Q8; no implementation may depend solely on plugins truthfully labelling individual model requests.
The current broker only lends authority to a live invocation (`packages/backend/src/plugins/runtime-capabilities.ts:131`); current model resolution requires a session. Add a host-owned background invocation lease rather than a fabricated SDK session or a retained factory port. A plugin schedules domain work; the host starts each invocation and supplies only that invocation's capabilities. Application/window lifetime and model-selection policy are Q3.
Only the host enable/budget control creates consent: show category, plugin/source, model/data destination, daily amount, unit, reset boundary and covered purposes. Default is off, including existing legacy `enabled: true` records. A background tick with no grant returns denied and performs no model request; it must not trigger recurring dialogs. Raising the limit, widening model scope or re-enabling requires a host decision. Plugins can inspect redacted remaining budget and request work, never set limits or mark themselves enabled.

Proposed durable host shapes; `DailyBudgetPolicy` and `ModelScope` require Q1–Q3 before their final schema is implementable:

```ts
type BackgroundModelGrant = {
  id: string; category: "background-model-spend";
  source: { pluginId: string; contentHash: string };
  enabled: boolean; generation: number; issuedAt: string;
  dailyBudget: DailyBudgetPolicy; modelScope: ModelScope;
};
type DailySpend = {
  bucketId: string; periodKey: string; policyRevision: number;
  settled: number;
  reservations: readonly {
    id: string; grantId: string; generation: number;
    sourceHash: string; selectionHash: string; bound: number;
    state: "reserved" | "dispatched" | "unsettled";
  }[];
};
```

Store `{schemaVersion: 1, grants, days}` in proposed `agentDir/plugin-background-model-spend.json`, StorageRegistry ID `agent-plugin-background-model-spend`, owned by one host service shared across windows. Use JsonStore for both consent changes and accounting; plugins receive neither this path nor a writable root containing it. Reject root selections that would expose host authorization/accounting files. The daily ledger is independent of plugin maintenance histories, task budgets and imported state. Budget bucket allocation/reset definition is Q1/Q2, not inferred from the illustrative grant list.

Host enforcement sequence (all model entry paths used by these jobs must reach this boundary):

1. Resolve current source, live lease, model/profile and host-known input/output bounds. Validate enabled grant/generation and allowed selection. Refuse unknown/unbounded accounting; nullable provider usage is never zero/free (`packages/plugin-api/src/runtime.ts:190`).
2. In one serialized durable update, require `settled + sum(outstanding bounds) + next bound <= user limit`; reserve and read back before dispatch. Persist reservation ID, period key, grant/source/model identity. Include every tool step, retry and parallel path, not just the outer job. For monetary budgets, a host-verifiable conservative price bound is necessary; a plugin estimate or post-call cost check cannot enforce a hard ceiling.
3. Recheck generation after reservation and immediately before dispatch. Mark dispatch durably. Invoke only through the existing session-engine SDK adapters; do not give plugins provider clients/credentials. Finish accounting even when publication is cancelled or revoked.
4. Settle using host-observed usage under the chosen unit. Release unused reservation only when non-dispatch or final accounting is proven. Unknown charge/failure or crash keeps its bound outstanding; restart cannot reset spent/reserved totals. Recovery must not auto-enable old plugin settings. A call spanning midnight settles against its original period; a new period does not erase outstanding liability. Clock rollback cannot refill a bucket (Q2 defines the day policy).
5. A store corruption/write/readback failure prevents dispatch; do not use JsonStore's read fallback as a fresh budget. Use the update/checked-write path and surface failure. JsonStore's queue is process-local: obtain exclusive host ownership of this accounting file before enabling dispatch; a second process must refuse ownership rather than run a second ledger.

Revocation is a durable generation change serialized with reservation/dispatch. It stops new/queued work, aborts active requests, drops late model output and downstream state publication, but still settles real charges. Source changes invalidate authorization. Disabling/re-enabling or replacing a grant cannot erase the same day's accounting. Do not promise to undo charges already dispatched.
Invalidate the live lease immediately even if saving revocation fails; report that persistence failure and prevent further dispatch. A later accounting error must never reinstate live authority.
Denial follows the current string-error transport: `Plugin capability denied: model.background.generate` (or toolStep). Budget exhaustion has a distinct host-authored message, `Background model daily budget exhausted`; cancellation/revocation rejects and publishes no result. Unknown accounting returns an explicit accounting-unavailable failure. Tests assert zero provider dispatch on all pre-dispatch failures. There is no foreground-model fallback, silent provider switch or plugin-enforced daily counter.

## Capsule per-export confirmation

Existing carrier: `packages/backend/src/plugins/session-capabilities.ts:171` implements `session.confirm`; `packages/backend/src/session-engine/session-questions.ts:6` calls the actual SDK UI; `packages/backend/src/session/ask-gate.ts:53` authenticates the responding owner and handles cancellation. Question answers are ordinary data, not grants (`packages/plugin-api/src/runtime.ts:259`). Therefore a plugin asking a question and later submitting `confirmed: true` is insufficient.
The host export capability resolves/finalizes the capsule, destination and audience, binds their hash plus source/caller/generation, then asks through this carrier with a host-authored summary of contents and omissions. The host consumes the affirmative result within that same live call, checks bindings again, writes exactly those bytes through JsonStore, and reads back before returning the path/hash. Closing the owner, SDK reload, cancellation or changed selection invalidates the pending answer. No reusable approval token is exposed to the plugin and no consent is restored from the capsule.
When no writable live session/question route exists, AskGate cannot ask; refuse export until Q7 selects an application-scoped host confirmation path. Do not synthesize a session. Existing audience omission and metadata disclosure semantics stay unchanged pending Q7.

## Open questions (do not decide during implementation)

- **Q1 — daily budget meaning:** Currency, tokens or calls? If currency, which currency, authoritative price source and conservative bound for cache/reasoning tokens? Is the user limit global, per plugin, per model/account, or shared across maintenance/radar/replay/multipath/eval? No default amount is authorized. This blocks final budget schema/UI and accounting behavior, not the fixed category/off-by-default decision.
- **Q2 — day and accounting recovery:** Which timezone/reset boundary applies, how do clock/timezone changes behave, and how is unknown usage reconciled without forgiving possible spend? What retention/explicit recovery is allowed for outstanding reservations and accounting files? Never silently reset on restart/reinstall, corrupt data or grant replacement.
- **Q3 — background lifetime/model:** Which plugin owns maintenance/radar scheduling; can jobs run with no selected session/window or after all windows close? Which configured model/profile does the user authorize and what data may each job send? Existing session-only ports cannot answer this. Do not silently convert to session-only jobs or fabricate SDK context.
- **Q4 — consent reuse:** May subprocess consent persist across reload/app restart, for how long, and does manual revoke require fresh consent at next enable? Does background enabled consent resume after restart once source/accounting checks succeed? Activation-local subprocess records above do not claim durable reuse. No saved plugin settings can settle these questions.
- **Q5 — install plans:** Approved versions/artifact integrity for uv / zotero-mcp-server, platform-specific destinations, update behavior, and whether one combined prompt may cover their dependency chain? Which executable probes are included, and how are shared/global uv installations and generic MCP-owned children associated with a grant? Do not infer arbitrary shell/Python permission from a program name.
- **Q6 — state/cloud custody:** Exact existing roots/adoption consent and source ownership for research/analysis/Inquiry; authorized binary/blob transport preserving existing size/format limits; verified receipt producer contracts and the real task-terminal event. For WebDAV, exact configured endpoint binding, credential slot/Digest ownership and migration from legacy secret files remain unresolved. No relocation, broad root grant, new dependency or data deletion is authorized.
- **Q7 — export context/disclosure:** Which host dialog carries export with no writable session, and what summary of full checkpoint metadata is required for private/restricted/public audiences? Every export still needs confirmation; do not change audience omission policy or assume a cancelled/absent UI means approval.
- **Q8 — cohort and remaining migration:** Which exact offline plugin/API candidates are the parity targets and which workflow entry contracts let the host classify replay/multipath/eval? Local source paths are planning evidence, not proof of the locked installed artifact. Vendor evidence/discovery/Inquiry coverage is incomplete; do not edit vendor, locks or compatibility policy to hide it. Domain cutovers require manager-issued file allowlists.
