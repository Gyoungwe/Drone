## 1. Inventory: what the mechanisms actually expose

`—` means no handler setting/category, not an exemption for writes. S = `application-state-write`, C = compute preflight/effect consent (`compute-preflight` in receipts), M = `background-model-spend`. ## 2. Port seams and missing authority

### Common inputs: activation, caller, storage

- **Activation and live selection exist.** Desktop passes `backendServices.sessions` to `createDesktopRuntime` (`packages/desktop/src/main/index.ts:467`); MAIN receives the canonical `source`, an approving window owner, and the activation signal via the capability provider (`packages/desktop/src/main/ui-plugins/runtime-host.ts:50`, `packages/backend/src/plugins/runtime-capabilities.ts:270`). Use `getPluginCallerContext` and exact live session identity, not renderer IDs or cwd as authority. The registered entry yields `workspaceId` from canonical project ID, `sessionId`, workspace directory, trust, read-only and session signal (`packages/backend/src/services/session-api.ts:123`, `packages/backend/src/plugins/session-caller.ts:16`). `Scope` needs both source hashes as well (`packages/plugin-api/src/p5-receipts.ts:28`). No P5 session scope for application-only callers or bootstrap.
- **Source hashes exist; P5 projection is absent.** Installed discovery computes `contentHash` (`packages/desktop/src/main/ui-plugins/installed-package-sources.ts:312`). For direct calls, the source closed over by MAIN is both caller and provider; require its current hash and a live session. For nested dispatch, use the broker-owned original consumer and current provider from the checked lineage (`packages/backend/src/plugins/coordinator.ts:273`, `packages/backend/src/plugins/coordinator.ts:278`, `packages/backend/src/plugins/coordinator.ts:310`). No typed P5 nested hash projection is supplied today (`packages/backend/src/plugins/runtime-capabilities.ts:21`); keep nested receipt/effect paths unavailable unless both roles can be proven, not two copies of the provider hash. Never derive current scope from a receipt being read.
- **Staging owner adapter is absent.** `P5StagingOwner` adds `callerId`, `action`, `signal` to the four scope fields (`packages/backend/src/plugins/p5-byte-staging.ts:9`). Coordinator owns a revocable selection token/object and binding/session lifetime (`packages/backend/src/plugins/coordinator.ts:153`, `packages/backend/src/plugins/coordinator.ts:182`); the broker exposes opaque caller/session identities and per-call cancellation, not a stable owner ID, action or signal for multiple chunks (`packages/backend/src/plugins/runtime.ts:607`, `packages/backend/src/plugins/runtime-capabilities.ts:198`). Bind a host-issued ID to that exact live attachment and a host-owned action/transfer lifetime; use the same owner/signal object for open/chunk/seal/use/cancel, and the call signal separately for individual effects. Switch/close/revoke must invalidate it. No plugin JSON, display ID, per-chunk composite signal or persistent receipt can substitute.
- **Receipt/fact storage inputs exist, P5 wiring does not.** Use the real host profile (`app.getPath("userData")`) and backend `StorageRegistry` already supplied to MAIN (`packages/desktop/src/main/ui-plugins/runtime-host.ts:59`, `packages/backend/src/services/session-api-diagnostics.ts:21`). Compose one host-private R1/F1 path per profile and storage ID; let each factory register/check the path and create its `JsonStore`. P5 paths and instances are absent at base, not plugin-selected dirs. The existing `plugin-execution-receipts` store is a different contract (`packages/desktop/src/main/ui-plugins/runtime-host.ts:146`, `packages/backend/src/plugins/execution-capabilities.ts:79`); do not adapt its records into P5 receipts. Use host wall-clock ISO timestamps for `now` (host clock precedent: `packages/backend/src/services/compute-adapter.ts:629`). R3 observation is opt-in via the existing guarded `observe` hook (`packages/backend/src/plugins/runtime-capabilities.ts:65`, `packages/backend/src/plugins/runtime-capabilities.ts:265`), not a blanket conversion of existing receipts; only actual host effects may supply expected/actual readback or usage.

## 4. Ownership and teardown

1. Keep durable stores outside activation lifetime; construct handler closures, W1/T1 review issuers, the T3 runs map, and staging state per activation (owner partition within activation, not process-global). B2 leases follow the exact owner; W2 gets a new reservation owner each invocation with a realpath-resolved output root. Do not reuse a stage ref across restart/source switch or let a foreign caller reach B1's ref lookup (`packages/backend/src/plugins/p5-byte-staging.ts:160`).
2. Stop new calls, abort exact caller/activation and unsubscribe F5 before release. Runtime already aborts then waits for pending invocations before port `dispose` (`packages/backend/src/plugins/runtime.ts:532`, `packages/backend/src/plugins/runtime.ts:540`). Register future batch/effect cancellation at abort time, not only inside the later disposer: T3 currently exposes no all-runs dispose/abort hook (`packages/backend/src/plugins/p5-batch-lifecycle.ts:111`). Abort its active controllers, wait for `done`/cleanup, then discard the map; reopened status may reconcile durable receipts only. Unsubscribe and drain F5 and real Z2 producer subscriptions before their owners close (`packages/backend/src/plugins/p5-host-delivery.ts:106`, `packages/backend/src/plugins/p5-host-delivery.ts:117`).
3. Drain P5 work before tearing down resources it uses; then close/invalidate staging and complete resource/transaction cleanup. B1's owner abort already invalidates refs and attempts cleanup (`packages/backend/src/plugins/p5-byte-staging.ts:69`, `packages/backend/src/plugins/p5-byte-staging.ts:180`); stage-owner lifetime/cancellation must coordinate with active consumers, and a notification alone is not verified cleanup. Preserve failed-cleanup evidence and leases; do not report success or follow a moved root.
4. Compose `dispose` and `finalRelease` separately; release P5 and existing resource reservations only after cleanup succeeds. Preserve native/domain/resource order and failure propagation from the registry (`packages/backend/src/plugins/runtime.ts:544`, `packages/backend/src/plugins/runtime.ts:568`). Desktop resource ports already split drain/release; current MAIN wrapper drains resource/execution concurrently when legacy execution is present (`packages/desktop/src/main/ui-plugins/desktop-resource-capabilities.ts:333`, `packages/desktop/src/main/ui-plugins/runtime-host.ts:189`). Put P5 drain before its dependencies, not another concurrent sibling if it still uses them.
